00 · Header

DI + Webex Calling Coexistence

T5 · Dedicated Instance

Dedicated Instance and multi-tenant Webex Calling can share one Control Hub org. Calls between them use certificate-based trunks Cisco already built. You activate those trunks. You do not edit them. A user is on one call control, not both.

Room T5-R05 Version v0.1 last-verified: TODO Difficulty L3 Est. time 90–110 min Prereq T5-R02 Reading 17 min

Key takeaways

  • Activation creates certificate-based SIP trunks over the Webex backbone. Calls wait until you activate them and add a main number. [cite:1]
  • Multi-tenant objects are prefixed WXC-DI. Dedicated Instance Unified CM objects are prefixed xWxC. Do not modify or delete them. [cite:1] [cite:2]
  • An old registration trunk has to be repointed. The example is xWxC route list to xWxC_MT route group. [cite:1]
  • Keep contiguous numbers, and keep pickup, hunt, and manager/secretary, on one call control. Each user is Dedicated Instance or multi-tenant, not both. [cite:3]
  • Calls through Dedicated Instance in the interop article are G.711 U-law, G.711 A-law, and OPUS only. That header is September 03, 2024. re-check [cite:1]

01 · Executive summary

Five lines, then why it matters

  • If you need calls between the platforms, fold the preconfigured elements into both dial plans. [cite:1]
  • Configure a PSTN connection on the default WXC-DI location before the main number. Until that number exists, users cannot make or receive calls through that route group. [cite:1] [cite:2]
  • On multi-tenant, new route lists and dial plans must select the route group tied to the certificate-based trunk. [cite:1]
  • One local gateway can hold two trunks. The deployment-model article still recommends a site be entirely on one platform, so a given gateway usually has one of those trunks. [cite:3]
  • Directory synchronization into Dedicated Instance Unified CM from Control Hub works only when SSO is enabled. [cite:3]
Why it matters. Mixed estates fail when a hunt group is split, a registration trunk is left in the route pattern, or the WXC-DI location has no main number. Peering link count stays in T5-R02. This room is the dial plan between the two calling platforms.

03 · Core concepts

What Cisco prebuilds, and what you still must do

Prebuilt, not finished

Service activation establishes SIP connectivity and basic dial-plan elements. If you need calls between the platforms, you incorporate those elements into the Webex Calling dial plan and the Dedicated Instance Unified CM dial plan. [cite:1]

Do not edit the objects

You are advised not to modify or delete the preconfigured interoperability dial-plan elements. The base-configuration article says the default trunks Cisco created should not be modified or deleted. There is one such trunk to each Dedicated Instance data center in the region. [cite:1] [cite:2]

Registration trunks are the old path

Some customers already deployed registration-based trunks. Link the existing route list and dial plan to the certificate-based route group. The Dedicated Instance example says xWxC route list should now point at the xWxC_MT route group. Route patterns that point directly at registration-based trunks must move. [cite:1] re-check

Not both

For calling services, each user belongs to Dedicated Instance or multi-tenant, not both. Calling features are not fully harmonized. Keep group features on one platform. [cite:3]

Glossary

Interop trunk
The certificate-based SIP trunk Cisco creates between Dedicated Instance and multi-tenant Webex Calling over the Webex backbone. [cite:1]
WXC-DI location
The default multi-tenant location. It needs a PSTN connection and a main number before calls use its route group. [cite:2]
ECBN
Emergency callback number on that location. When set, an emergency call presents it to the PSTN provider. [cite:1]
X-DI-WxC-otg
SIP header the normalization script adds toward Webex Calling. [cite:2]
Group filter
Limits Dedicated Instance Unified CM directory sync to users designated for Dedicated Instance. [cite:3]
CCP for both
The deployment-model article says both multi-tenant and Dedicated Instance users can use existing Cloud Connect PSTN partner peering to the multi-tenant platform. [cite:3]

06 · Config

Activate the trunk without renaming it

  1. Sign in at admin.webex.com. Open Management → Locations. Select the default location prefixed WXC-DI. Open Calling, then Manage in the calling connection. [cite:1]
  2. On connection type, select the default route group prefixed WXC-DI, check the disclaimer, and continue. Add the main number now or accept that calls wait. [cite:1]
  3. On the same location, set Callback Number under Emergency Calling and save. [cite:1]
  4. Under Services → Calling → Call Routing, confirm certificate-based trunks in the trunk-type column. Create the route list and the dial plan with that route group as the routing choice. [cite:1]
  5. On Dedicated Instance, point the xWxC route list at the xWxC_MT route group. Move any route pattern that still targets a registration trunk. [cite:1]
  6. Leave the default trunks in place. Update the RedSky account ID. Do not invent a new interop trunk name. [cite:2]
  7. Assign each user to one calling service. Keep contiguous numbers and group features together. [cite:3]
  8. If agents are on Dedicated Instance for Webex Contact Center, copy Factory Default Lossy, order G.711 U-law, G.711 A-law, OPUS, and apply that list on the regions the integration article names. Do not do that reorder for a non-WxCC trunk just because the interop article lists the same three codecs. [cite:4] [cite:1]

09 · Self-question ladder

Twelve rungs

L0What connects Dedicated Instance to multi-tenant calling?

Certificate-based SIP trunks over the Webex backbone, created at activation. [cite:1]

L1Why is activation not enough for a test call?

You still incorporate the elements into both dial plans, and the default location needs a PSTN connection and a main number. [cite:1] [cite:2]

L2Which prefixes do you protect?

WXC-DI on multi-tenant and xWxC on Dedicated Instance Unified CM. [cite:1]

L2How many interop trunks does the base article describe in a region?

One to each Dedicated Instance data center. [cite:2]

L3How do you prove a registration trunk is still in the path?

The route pattern or route list still targets it. The fix is the certificate route group. [cite:1]

L3What header identifies the cluster on the Webex Calling side?

X-DI-WxC-otg, added by the normalization script. [cite:2]

L4How is this different from a Unified CM to multi-tenant migration coexistence?

That path uses a local gateway between on-premises Unified CM and Webex Calling. This path is Dedicated Instance already in the cloud, with Cisco’s certificate trunks. T6-R07 is the on-premises coexistence room. [cite:1]

L4Can one person be a calling user on both?

No. The deployment-model article says not both. [cite:3]

L5Why might you still migrate everyone to Dedicated Instance before you split?

The same article says Dedicated Instance can come first, and then you divide the user base. Contiguous numbers and group features stay together when you divide. [cite:3]

L5When do you reorder codecs?

The contact-center integration says to reorder only for WxCC. The interop article already limits Dedicated Instance-directed calls to those three codecs. Do not treat the two sentences as one procedure. [cite:4] [cite:1]

L2What does a missing main number block?

Make and receive through the route group for that default location. [cite:1] [cite:2]

L1Why does SSO sit in a dial-plan room?

Because Dedicated Instance user sync from Control Hub is unsupported without it, so the split never becomes real on the cluster. [cite:3]

13 · Interview

Oral answers

30 seconds. Dedicated Instance and multi-tenant Webex Calling interoperate with certificate trunks Cisco creates over the Webex backbone. Multi-tenant names start with WXC-DI. Unified CM names start with xWxC. You add a PSTN connection and a main number, and you point your dial plan at the certificate route group. You do not rename those trunks.

2 minutes. Older registration trunks have to be unhooked. The route list example points at the multi-tenant route group Cisco built for the certificate trunk. A user is on one calling service. Contiguous numbers stay together. Pickup, hunt, and manager/secretary stay on one platform because the features are not fully harmonized. A gateway can trunk to both, and the article still wants a site on one platform. Directory sync onto the dedicated Unified CM needs SSO. A group filter keeps multi-tenant users off that cluster.

30 seconds, codecs. The interop article allows G.711 U-law, G.711 A-law, and OPUS for calls directed through Dedicated Instance. The contact-center article wants that order, U-law first, and only when agents are on Dedicated Instance for Webex Contact Center. Both pages are older than a year. Re-read them.

2 minutes, meetings and PSTN. Cloud Connect PSTN on the multi-tenant peering can serve both populations in the deployment story. If you are not using that, the interop location can be premise PSTN. Meeting call-me in that story comes through Cisco’s internal trunk to Dedicated Instance. The normalization script adds X-DI-WxC-otg so Calling knows which cluster it is. You still type the RedSky account ID yourself.

What you will not say. You will not say a user can subscribe to both calling services. You will not delete WXC-DI-TRK. You will not treat the Edge Connect 3.0 “one peering path” sentence as permission to ignore the two Dedicated Instance connections in T5-R02.
